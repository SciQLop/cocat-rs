# Phase 0 Spike Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `cocat-server` binary that serves `/room/{id}` over the Yjs sync protocol, authenticated from the Python server's SQLite and JWT, fast and stable enough to pass the design's go/no-go gates.

**Architecture:** One Cargo workspace with `cocat-core` (the `.y` file store, room-id and role types) and `cocat-server` (axum websocket, sqlx reads of the Python schema, one tokio task per room owning a `yrs::Doc`). A Python benchmark harness measures both servers with the real client stack; the Python test suite drives the Rust binary through a new live mode.

**Tech Stack:** Rust 2024, `yrs` 0.28, `axum` 0.8, `tokio`, `sqlx` 0.9 (sqlite), `jsonwebtoken` 11, `argon2` 0.6, `clap` 4, `uuid` 1, `bytes`, `thiserror`, `tracing`; `tokio-tungstenite` and `tempfile` for tests. Python: `httpx`, `websockets`, `pycrdt`, `pytest`.

**Spec:** `docs/superpowers/specs/2026-11-05-cocat-rs-design.md` (phase 0 and its gate table)

## Review Focus

These are the conditions most likely to bite, and the tests that pin them:

1. **A `.y` file whose tail was cut mid-record** (crash, disk full) — the room must open with every intact record, not fail and not lose them. → `stops_at_a_truncated_record` (Task 1), `append_after_a_truncated_tail_rewrites_from_the_good_offset` (Task 2).
2. **A socket that sends a 0- or 1-byte frame, or garbage** — the room task must drop the frame and keep serving every client. → `frames_shorter_than_two_bytes_are_ignored` (Task 5), `short_frames_do_not_close_the_socket` (Task 6).
3. **A viewer sending a `SyncStep2`** (their local state on connect) — it must not mutate the document, while their `SyncStep1` is still answered. → `a_viewer_sync_step2_is_dropped_but_their_step1_is_answered` (Task 5), `viewer_update_does_not_land` (Task 6).
4. **Two clients writing at once** — both updates land in the document and in the file, and each client sees the other's. → `two_clients_updates_both_land_and_both_are_broadcast` (Task 5).
5. **A room id that is empty, has `..` or a `/`, or whose file is missing** — reject the id, never resolve outside `--update_dir`; a missing file is a new empty room. → `rejects_an_invalid_room_id` (Task 1), `a_missing_file_opens_as_an_empty_room` (Task 1).

## Decisions this plan fixes

- The live slice is five `test_routes.py` tests, not ten: the kick/role/delete tests need `/api/*`, which is phase 1. The gate report records the smaller number.
- `COCAT_SERVER_CMD` selects the binary for both `serve` and the seeding CLI; `COCAT_TEST_SERVER_URL` (optional) points at an already-running server instead of spawning one per test.
- The harness is Python with the real client stack, so the Python baseline and Rust are measured by the same code.
- `serve --port 0` binds an ephemeral port and prints `listening on 127.0.0.1:<port>`, which the Rust integration tests and the harness use.
- `add-user-to-room` takes `--role {editor,viewer}`, default `editor`, because the viewer tests seed a viewer without the REST API.
- The spike's schema bootstrap writes the Python table shape (`user.rooms` is `NOT NULL`, so inserts write `'[]'`), and `serve` opens the database read-only.

### Task 10: The benchmark harness

**Files:**
- Create: `bench/make_room.py`, `bench/harness.py`, `bench/README.md`
- Test: a smoke run of each scenario with tiny parameters.

**Interfaces:**
- `make_room.py --dir --room --catalogues 100 --events 1000` writes `varuint(len) + update` records after the `0.0.1\0` header and prints the file size.
- `harness.py <open|fanout|scaleout|soak|openclose> --server-cmd --db --update-dir --email --password [--json out.json]` spawns the server, logs in over HTTP, opens N raw websockets, and prints/records: `rss_peak_mb`, `rss_end_mb`, `cpu_seconds`, `open_p50_ms`, `open_p95_ms`, `fanout_p50_ms`, `fanout_p99_ms`, `updates_per_s`, `lost_updates`.
- Scenario parameters: `open` = 20 cold connects to the 100k room; `fanout` = 50 clients, one editor, 1 update/s, 300 s; `scaleout` = 1 room × 8 clients and 8 rooms × 8 clients (1k-event rooms), 60 s each at 10 updates/s per room; `soak` = 1 room, 50 clients, 3600 s, 1 update/s; `openclose` = 20 connect/receive/disconnect cycles on the 100k room.

- [ ] **Step 1: Write `make_room.py` and check its output**

Run: `.venv/bin/python bench/make_room.py --dir /tmp/spike/updates --room bench100k --catalogues 100 --events 1000`
Expected: prints a size near 38 MB.

- [ ] **Step 2: Write `harness.py` with a `--smoke` flag**

`--smoke` shrinks every scenario to 2 clients and 2 s. Clients are raw websockets that do not keep a `Doc` (50 Docs of 100k events would not fit in memory): latency is `perf_counter()` at receipt minus the send time recorded in `sent[hash(frame)]` in the same process. RSS from `/proc/<pid>/status` every 5 s; CPU from `/proc/<pid>/stat` at start and end. Lost updates = tokens sent minus tokens present in the final state (tokens are `Y.Map` keys `t-<n>`).

- [ ] **Step 3: Smoke every scenario against the Python server**

Expected: each exits 0 and prints a JSON object with every key.
