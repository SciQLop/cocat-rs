# Phase 4a: the access matrix and the frame fuzzer

## The access matrix

`crates/cocat-server/tests/access_matrix.rs` drives every route the server serves against
every kind of caller: 94 rows, 11 callers, 1034 checks. The callers are anonymous,
unverified, deactivated, a stranger, a room viewer, editor and owner, a viewer, editor and
owner reached through a group, and a superuser. Each row states the guard, the kind of
refusal a caller outside the guard gets (403 or the 404 Python shows for something you
cannot see), and the scope that makes a caller "inside" it.

`every_route_is_in_the_matrix` reads the router sources and fails when a route has no row,
so a new endpoint cannot ship untested. `every_route_answers_every_caller_as_the_table_says`
runs the checks, one fresh world per (row, caller) so a destructive request cannot change
what a later caller sees.

### Corrected rows

No code was wrong; every mismatch was a row that described the wrong guard or scope.

- `POST /auth/jwt/logout` is `SignedIn`, not public.
- `PATCH /api/rooms/{room}` and `POST /api/rooms/{room}/owner` admit members reached through
  a granted group, while `DELETE /api/rooms/{room}` was recorded as direct-member-only. Both
  rename and delete go through `lifecycle::require_role`, which reads the effective role from
  `db::role_in`, so a group editor gets 403 on both; the earlier 404 was an artefact of
  sharing one world across callers — the owner's delete in the same row removed the room
  before the group callers ran. The row is now `RoomAny`, and the loop builds a fresh world
  per (row, caller).
- `DELETE /api/rooms/{room}/members/{member}` is owner-only.
- `/users/*` answers 403 to any signed-in non-superuser.
- `GET /api/rooms/{room}/catalogues` and the legacy `/room/{id}/users` answer 404 to
  non-members.
- Room invitation routes and room group grants treat group-reached members as members.
- `PUT /api/rooms/{room}/groups/{spare}` needs a group the caller belongs to.
- Group routes scope their refusals to group membership; the group member delete and the
  room un-grant accept either 403 or 404, so those rows are marked loose.

The matrix takes about 33 s, almost all of it seeding a world per check.

## The frame fuzzer

`crates/cocat-server/tests/frame_fuzz.rs` sends sequences of hostile websocket frames to a
real room and checks four invariants after each sequence:

1. A viewer's frames never change the room state.
2. The room thread is still alive: a fresh client syncs, and a valid editor update reaches
   another client within 2 s.
3. The process RSS stays under +256 MB over the run.
4. The room file, reopened with `FileRoomStore::open`, holds the state the room serves.

Generators mix structured y-sync messages (state vectors, updates, trailing bytes, other
message types) with raw bytes up to 64 KiB, including hand-built v1 frames whose state
vector is arbitrary. The default run is 24 cases (6.6 s); `FUZZ_CASES=2000` raises it.

Runs: 24 cases in 6.64 s, all green; `FUZZ_CASES=2000` in 217.02 s, all green.

### Finding: a hostile state vector killed the room thread

A single `SyncStep1` frame whose state vector carries a client id above the value yrs can
represent made `StateVector::decode_v1` panic inside the room thread. The decode happened
before the role check, so even a viewer could end a room; every client of it then lost sync.

- Reproducer: `a_frame_that_breaks_the_decoder_is_dropped` in `src/room.rs`.
- Fix: commit `1e39b90` "Survive a frame the decoder cannot read" — both decoder calls
  (`Message::decode_v1` and `Update::decode_v1`) now catch a panic and treat it as another
  undecodable frame, so a value yrs cannot represent costs one frame instead of the room.

No other invariant failed, and no other frame shape changed state or wedged a room.
