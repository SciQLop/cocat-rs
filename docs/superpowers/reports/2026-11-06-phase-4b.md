# Phase 4b — Attacker campaign report

Three agents, each with the same brief (enter a foreign room, take over an account, write
as a viewer, exhaust the server, steal tokens), attacked their own instance of `main` at
`d3d3ce3`. Each had the source, a live server, a superuser account and a mail directory, and
had to prove every finding with a Python script exiting 1 on a vulnerable server. Every
reproducer was rerun twice by the reviewer on a freshly started server before it was
accepted. Fixes: `docs/superpowers/plans/2026-11-06-phase-4b-fixes.md`.

| Attacker | Model (OpenCode Go) | Time | Findings |
|---|---|---|---|
| 1 | DeepSeek V4.1 Flash | ~30 min | 5, all reproduced |
| 2 | MiMo V2.6 Flash | ~2 h 30, stopped | none; never wrote its report |
| 3 | GLM-5.3 Flash | ~40 min | 2, both reproduced (one shared with attacker 1) |

Qwen3.8 Flash was tried first as attacker 3: its provider answered "not valid JSON" on every
turn once the context grew, so it was replaced. Attacker 2 kept probing after it was told to
write its report; its coverage is unverified.

Finding 6 was found by the reviewer while reading the login code for 1-03, and measured on a
live instance before the fix.

### How 3-02 was fixed (three rounds)

1. `5abbbff` stored yrs's own diff for the transaction (`encode_update_v1`). Correct, but it
   walks every client id the document has seen: 40 000 updates from fresh client ids took
   26.6 s instead of 0.8 s, so any editor could slow a room quadratically. The websocket
   slow-client test had caught it and been rewritten to pass; it was restored.
2. `2f77730` keeps a state vector owned by the room thread and compares only the clients an
   update carries (from `Update::insertions`, since `Update::state_vector` counts only blocks
   starting at clock 0). Back to 0.8 s. The original payload is stored when it is new.
3. `19d3e77` raises that state vector only through ranges contiguous with it: an update
   arriving before the one it depends on had made the earlier one look like a repeat, which
   would have dropped it from the file and from the other clients.

## Storage limits (user decision)

`COCAT_ROOM_MAX_MB` (default 1024) and `COCAT_OWNER_MAX_MB` (default 5120: the total of the
rooms a user owns). An update past the room's allowance is refused before it is applied and
its sender is closed with 4507. `014d613` fixed the defaults being read as bytes (the
correctness bench caught it).
`simplify:` the allowance is computed when a room opens; two open rooms of one owner can
each use the remaining quota.

## What the attackers tried that did not work

- **Foreign rooms:** websocket handshake (403 before upgrade, same for unknown ids), every
  `/api` and legacy route (uniform 404), path tricks on room ids (case, `%2f`, `..`, `%00`),
  group grants without room ownership, reattaching after removal (closed with 1008).
- **Writing as a viewer:** `SyncStep2`, `Update`, truncated and unknown frames over the
  websocket (dropped, file unchanged), every API route and UI form.
- **Account takeover:** forged cookies (`alg: none`, other algorithms, bad signatures),
  cross-use of reset/verify/session tokens, reset links after use, sign-up races, email
  change, flag injection at registration, `PATCH /users/{id}` without superuser,
  invitation acceptance by another address, deactivated users acting.
- **Tokens:** only in URL fragments and POST bodies, never in logs, redirects, errors or
  flash cookies; the secret file is 0600 and never served.
- **Web:** XSS (askama escapes everything), open redirects through `next`, mail header
  injection, SQL injection (every query is bound), header injection in the VOTable download.
- **Rate limits:** `X-Forwarded-For` cannot rotate the key while no proxy is trusted.

## Leads not proven (kept for later)

- A large catalogue export on a room that is open blocks that room's sync while it runs.
- Outbound queues are bounded in frames (1024), not bytes; frames are shared `Bytes`, and the
  5 s write timeout drops a client that stops reading.
- One OS thread per open room: 300 connections to 300 rooms are 300 threads.
- The login rate limiter's key includes the path; a proxy that rewrites paths would split it.
